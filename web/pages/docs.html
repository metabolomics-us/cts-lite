Documentation

CTS-Lite is a lightweight Chemical Translation Service, and the successor to the Fiehn Lab's original CTS. It allows users to easily match Compound Names, InChIs, InChIKeys, SMILES, Molecular Formulas, PubChem CIDs, HMDB IDs, and CAS IDs against the 100+ million compounds from the PubChem database.

Using CTS-Lite

To use CTS-Lite, enter your queries into the input box on the main page, preferably one entry per line. When you click Match, the results will be displayed in the section below. Results can be downloaded in JSON and CSV formats using the download button. See Entering Queries for how lines with several words are interpreted by the server.

Note: There is a limit of 100,000 entries per request. With ClassyFire enabled, the limit is reduced to 1,000 entries. Very large queries may take some time to process. Please be patient while the server handles your request.

Entering Queries

The recommended way to enter queries is one entry per line. A line holding a single entry is read as that entry, including names with spaces like lactic acid.

Note: A name longer than 10 words is the one exception, since it would be split into words. Wrap the line in double quotes or force the query type to be 'Name'.

Several Entries on One Line

If it is more convenient to separate entries with spaces (for example when pasting a space-separated list), CTS-Lite has to guess whether a line is one name or several entries. Quoting each entry removes the guesswork. Otherwise, with the Query Type set to Auto (the default), a line with several words is read as follows:

  • Names stay whole: lactic acid is one entry
  • Lists of identifiers are split: CCO H2O 2244 is three entries. If the whole line is a known compound name it stays whole instead
  • Lines over 10 words are always split: 99.9% of PubChem names are 10 words or fewer
  • Mixed lines are read as one name: A line mixing names and identifiers, like C6H12O6 lactic acid, is looked up as a single name (unless the identifiers are 'strong' identifiers, which include InChIKey, InChI, CAS ID, or HMDB ID, in which case each word is queried individually)

A forced query type changes these rules: a forced Name keeps every line whole as one name, with no 10-word cutoff, and any other forced type splits every line on spaces.

Quoted Entries

Wrap an entry in double quotes to guarantee it is not split on spaces

  • "lactic acid" "malic acid" is two entries
  • C6H12O6 "lactic acid" is read correctly as two entries

Query Types

By default (query type Auto), CTS-Lite detects the type of each entry from its format. The accepted formats are:

  • Compound Name: any PubChem name or synonym, case-insensitive, e.g. caffeine
  • PubChem CID: a whole number from 1 to 500,000,000, e.g. 2519
  • InChIKey: 27 uppercase characters in 14-10-1 blocks, e.g. RYYVLZVUVIJVGH-UHFFFAOYSA-N
  • InChI: starts with InChI= (case-sensitive), e.g. InChI=1S/H2O/h1H2
  • SMILES: e.g. CN1C=NC2=C1C(=O)N(C(=O)N2C)C. SMILES with no exact match are converted to an InChIKey and searched again with query type 'Converted SMILES' when matched (see RDKit Conversion)
  • Molecular Formula: e.g. C8H10N4O2
  • CAS ID: with a valid check digit, e.g. 58-08-2
  • HMDB ID: HMDB followed by 1 to 7 digits, e.g. HMDB0001847. Legacy 5-digit IDs (HMDB01847) are padded to 7 digits

Some entries, like CO, are valid as both SMILES and molecular formula. These are tried as SMILES first, then as a formula. Avoid this ambiguity by forcing the query type.

Force a Query Type

To query every entry as one type, choose it under Query Type in the settings panel, click its label above the input box, or add query_type=... to an API request (see Request Parameters). Only that lookup runs, which helps when an entry could be read as more than one type.

Malformed Queries

Entries that look like an identifier but cannot be a valid one are reported as malformed and are not looked up:

  • InChIKeys with lowercase letters or blocks of the wrong length
  • InChIs that start with InChI=, but with improper capitalization, i.e. inchi=
  • PubChem CIDs that cannot be valid. This includes zero, numbers with leading zeros, and numbers above 500 million
  • CAS IDs whose check digit is wrong, like 58-08-3
  • HMDB IDs with no digits or more than 7 digits

Entries with no letters that fit none of the formats, like ???, are reported as unidentified. Anything else with letters is searched as a compound name.

Match Levels

Every match reports a match_level describing how it was found. In the web UI, results can be narrowed to one kind of match level using the filter button beside the 'Results' label.

Exact Matches

The query matched a compound in the CTS-Lite database exactly. The match level names the identifier that matched: Exact "query_type".

A SMILES or InChI that was matched through its converted InChIKey is reported as Exact InChIKey. An HMDB ID padded to 7 digits (HMDB01847 → HMDB0001847) is still an Exact HMDB match. The query that was used for these matches is returned in converted_query.

Name Variant Matches

A name with no exact match is retried with common lab spellings rewritten to the form PubChem uses. For example, gly pro matches as gly-pro. Such a match has the Name Variant level, and the rewritten name is returned in converted_query.

First Block Matches

Given the setting for first block matches is enabled (the default), "InChIKey" queries can match by first block if they don't find an exact match in the local database. This gives the First Block match level. "Converted SMILES" queries can also match by first block, since they are SMILES queries that were converted to InChIKey and then reattempted. The first fourteen characters of the InChIKey are the key's first block.

For example, the query XLYOFNOQVPJJNP-XXXXXXXXXX-X would be a first block match with Water, whose key is XLYOFNOQVPJJNP-UHFFFAOYSA-N.

Since a first block match is not considered a miss, that query is not sent to PubChem Live, even if PubChem would have had an exact match. If you want exact matches only, disable first block matching using the settings cog in the web UI or by adding first_block_matches=false to the API request.

PubChem Live Matches

Queries that do not find a match in the local database are forwarded to PubChem. A live lookup is performed against all 124 million compounds of PubChem. PubChem Live queries take longer than local database matches. Their match levels start with PubChem Live:, e.g. PubChem Live: Exact InChIKey.

Compound names, CAS IDs and HMDB IDs are searched in the CTS-Lite database only, and are never sent to PubChem Live.

A PubChem Live match can sometimes return something slightly different to the exact query provided by the user. For example, querying H4C will return CH4, and CH3COOH will return C2H4O2. This can even occur with some SMILES queries, because RDKit is used in the background to convert SMILES queries into InChIKeys before querying PubChem.

Top Hit Only

By default, CTS-Lite will return only the top hit per query. This setting can be toggled in the settings panel, or by adding the top_hit_only=false parameter to the API request.

For queries that are not of type 'Name', the top hit is determined by ranking the hits on a weighted relevance score:
(0.7 * literature_count) + (0.3 * patent_count)

The top hit for a name query is decided differently. Each compound has a list of names/synonyms ordered by relevance. The top hit is the compound that lists the queried name highest in its own list. Ties are broken by the weighted score above.

RDKit Conversion

The same compound can be written as many different SMILES strings, so a SMILES query with no exact match is converted to an InChIKey using RDKit and searched again. If the local database still has no match, that InChIKey is used for the PubChem Live lookup. InChI queries not found locally are converted to InChIKey the same way before searching PubChem.

A match found this way is returned with the query type Converted SMILES or Converted InChI. For a given query, you can click the "Query Type" bubble to expand it and see the InChIKey that was used instead.

Anno. Type Count

The "Annotation Type Count" indicates the number of PubChem categories (e.g. Taxonomy, Toxicity, Pharmacology, etc.) that a compound has been annotated with.

Well-researched compounds tend to have 10+ types, with an observed maximum of 20. The "Annotation Type Count" can be used as a supplementary confidence metric when comparing compounds.

Chemical Classification (ClassyFire)

STATUS: ClassyFire is currently unavailable. Chemical classification is temporarily disabled in CTS-Lite. Please try again later, or report a persistent outage to the issue tracker.

CTS-Lite can optionally provide chemical taxonomy classifications from ClassyFire, developed by the Wishart Research Group. Requests with ClassyFire enabled are limited to 1,000 entries.

ClassyFire is disabled by default due to the additional network latency it causes. Enable it from the settings panel, or via the API with the classyfire=true parameter. The stream=true parameter is recommended for ClassyFire requests, to help avoid timeouts.

Each matched compound receives the following ClassyFire fields (some may be empty and therefore omitted):

  • Kingdom: organic vs inorganic (e.g. Organic compounds)
  • Superclass: general structural identifiers (e.g. Organoheterocyclic compounds)
  • Class: specific structural features (e.g. Imidazopyrimidines)
  • Subclass: even more specific features (e.g. Purines and purine derivatives)
  • Direct Parent: most specific class (e.g. Xanthines)
  • Description: text description of the compound's chemical class

If a compound is not found by ClassyFire, or if the ClassyFire service is unavailable, the reason is reported in an error field.

A single query can match many compounds (for example, a molecular formula with top_hit_only=false may return hundreds of hits). To keep latency reasonable, only the top match of each identifier is classified.

Note: ClassyFire adds significant network latency proportional to the number of unique matched compounds in your query.

REST API

Request Formats

To make cURL requests using the REST API, use the following formats:

JSON (Standard):

curl -X POST \ -H "Content-Type: application/json" \ -d '{"queries":["citric acid", "RYYVLZVUVIJVGH-UHFFFAOYSA-N", "2244", "CCO"]}' \ "cts-lite.metabolomics.us/match"

CSV:

curl -X POST \ -H "Content-Type: application/json" \ -H "Accept: text/csv" \ -d '{"queries":["citric acid", "RYYVLZVUVIJVGH-UHFFFAOYSA-N", "2244", "CCO"]}' \ "cts-lite.metabolomics.us/match"

Request Parameters

Disable top hit only:

"cts-lite.metabolomics.us/match?top_hit_only=false"

Disable first block matches:

"cts-lite.metabolomics.us/match?first_block_matches=false"

Enable ClassyFire chemical classification:

"cts-lite.metabolomics.us/match?classyfire=true"

Specify a forced query type: (auto | name | smiles | inchikey | inchi | formula | pubchem_id | hmdb | cas)

"cts-lite.metabolomics.us/match?query_type=inchikey"

Enable NDJSON response streaming (helps prevent timeouts, CSV-incompatible):

"cts-lite.metabolomics.us/match?stream=true"

Combine several parameters by joining them with &:

"cts-lite.metabolomics.us/match?top_hit_only=false&classyfire=true&stream=true"
